# 権限モデル

## 基本構造

権限 = **主体 × 資源** の ACL。

- **主体**：User と Agent（永続 ID）。どちらも同じモデルで扱う
- **資源**：
  - **FS パス**：glob で表現（例：`repos/frontend/**` read-write、`shared/finance/**` read-only）
  - **MCP ツール**：サーバ単位またはツール単位の allowlist（例：`slack:send_message` は不可、`slack:read_*` は可）

## 職位ロールと組織木

主体は組織木のノードに属し、職位ロール（メンバー / 課長 / 部長 / 管理者）を持つ。

- ロールは権限の束（デフォルト ACL）を与える
- 組織木は**承認の経路**を決める：ある権限を持たない主体がそれを必要としたとき、承認者 = 「その権限を持つ最小の祖先」
- 日本企業の職務権限規程（決裁権限表）をそのまま ACL として写し取れることを設計目標とする

## 委任原則

Run の権限は起動者からの**委任**として決まる。

```
Run の権限 = Template の権限 ∩ 起動者の権限
```

- 原則：エージェントは起動者を超える力を持たない
- 例外：Template が起動者の権限を超える部分は、**起動時事前承認**（[approval.md](approval.md)）を経て初めて有効になる。承認されると Run はその超過分を含む権限で動く

Agent が永続 ID なのは、この権限と監査履歴を Run をまたいで蓄積するため。将来の常駐型エージェント（自分で仕事を拾う）にもこのモデルをそのまま適用できる。

## Enforcement：3 つのチョークポイント

エージェント本体（プロンプトや自己申告）は信頼しない。強制は実行経路上の 3 点に集約する。

| チョークポイント | 強制する対象 | 手段 |
|---|---|---|
| FS マウント | ファイルアクセス | Run コンテナには権限のあるパスだけをマウント（read-only / read-write を区別） |
| MCP ゲートウェイ | MCP ツール呼び出し | 全 MCP 通信を中央プロキシ経由にし、ACL 判定・監査ログ・レート制御を一元化 |
| API キープロキシ | モデル API | プロバイダのキーを Run に渡さず、プロキシで中継。利用量を主体・部門別に記録（課金配賦） |

prompt injection でエージェントが騙されても、権限外の資源には物理的に到達できない — これが多ユーザ環境で外部データを扱う際の前提となる防御線。

## 監査ログ

全ツール呼び出し・承認・却下・権限変更を append-only のイベントログに記録する。「誰が（どのエージェントが、誰の委任で）、いつ、何をしたか」を常に再構成できる。

## 未決

- ロール階層のカスタマイズ性（組織ごとに職位体系は異なる）
- ゲートウェイを通せない資源（エージェントが直接叩く外部 API 等）の扱い — egress 制御をどこまでやるか
