# 承認フロー

MVP で 3 種すべてを実装する（決定 D4）。いずれも「承認待ち」はボード上で全員に見え、承認権者だけがアクションできる。全件イベントログに記録。

## 1. 起動時事前承認（稟議型）

**タイミング**：Run 起動前。

**発火条件**：

- Template の権限が起動者の権限を超えている（超過分の委任が必要）
- Template またはボードの設定でコスト上限・事前承認必須が指定されている

**承認者**：不足している権限を持つ最小の祖先（組織木を上へ）。

**挙動**：承認されるまでカードは Ready に留まり「承認待ち」バッジが付く。却下時は理由がカードに記録される。

## 2. 危険操作の承認ルーティング

**タイミング**：Run 実行中。エンジンからの `permission_request` イベント（Claude Code の permission prompt に相当）を受けたとき。

**ルーティング規則**：

```
要求された操作が Run の権限内         → 自動許可（起動時に委任済み）
権限外だが起動者の権限内             → 起動者（または権限を持つ任意のユーザ）に確認
起動者の権限も超える               → その権限を持つ最小の祖先へエスカレーション
```

**挙動**：カードは Waiting（承認待ち）に移動。承認・却下・「今回のみ / この Run では常に許可」を選べる。ローカルツールの permission prompt の「チーム版」であり、本企画の中核機能。

**タイムアウト**：未決（O7）。候補：一定時間で上位へ再エスカレーション、または自動却下で Run を安全に停止。

## 3. 成果物レビュー関門

**タイミング**：Run 完了後。カードが InReview に移動したとき。

**レビュアー**：カード作成時に指定（人間）。未指定ならアサイン者の直属上長をデフォルトにする。

**挙動**：

- 承認 → Done
- 差し戻し → コメント付きで InProgress に戻り、同一カードに新しい Run を起動できる（前 Run の成果物とコメントがコンテキストとして引き継がれる）

ボード構造（列の遷移制約）だけで強制できるため実装が軽く、hooks（[hooks.md](../orchestration/hooks.md)）の「完了 → 上長に報告」パターンの受け皿にもなる。

## 通知

MVP はボード内の通知センターのみ。Slack / メール連携は hooks のアクションとして将来対応。
