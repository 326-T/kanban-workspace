# アイデンティティと来歴

## 原則

1. **真実は内部イベントログ、git はその投影**。「誰が・誰の委任で・どの承認を経て・何をしたか」の完全な来歴はイベントログが持ち、git のコミット履歴はそれをポータブルな形式に投影したもの
2. **アイデンティティは行為の文脈から導出する**。誰の行為かは「認証された主体 × Run」からプラットフォームが決定し、環境のグローバル状態（`~/.gitconfig` 等）には依存しない。ユーザが git config を意識する場面を作らない

## コミットの規約

**author = そのコミットを実際に作った主体**（決定 D5）。エージェントの Run ならエージェント名義（例：`writer-a <writer-a@agents.workspace>`）、人間の作業なら人間名義。来歴の詳細は trailer で参照する。

```
docs: 四半期報告の骨子を作成

Run: run_01JABC...
Launched-by: takeda
Approved-by: tanaka (成果物レビュー)
Co-Authored-By: 竹田 恭 <takeda@...>
```

- エージェントと人間のコミットが 1 ブランチに混在するのは正常であり、「どこまでエージェントがやれて、どこから人間が拾ったか」が正確に残る。エージェントの成功率・信頼度の計測データになる
- Run の未コミット変更を保全する **checkpoint コミット**（`Checkpoint: true` trailer 付き）をプラットフォームが自動作成できる。作業主体の切り替わりは常にコミットで区切られる

## 人間の作業も Run（決定 D6）

人間の作業セッションは `engine = human` の Run として扱う。カードの状態機械・レビュー関門・監査はエージェントと完全に同じレールに乗る。

**引き継ぎ**（エージェントができなかった → 人間がやる）＝ カードの再アサイン：

1. エージェント Run の未コミット変更を checkpoint コミットとして自動保存
2. 同じブランチ・worktree の上で human Run が始まる
3. 以降のコミットは人間名義。カードの来歴は途切れない

人間の作業経路は 2 本：

| 経路 | 仕組み | アイデンティティ |
|---|---|---|
| ブラウザワークスペース（舗装路） | カードの「引き継ぐ」→ worktree にアタッチした Web エディタが開く | プラットフォームが文脈から導出。git config 不在 |
| ローカル作業 | プラットフォームの git エンドポイントから clone。専用 CLI が clone 時に repo-local identity を自動設定 | pre-receive で「author = 認証ユーザ」を検証。手元の設定が壊れていても誤名義は混入しない |

## 外部アイデンティティ：第 3 の資源タイプ（決定 D8）

「GitHub の自分のアカウントで push する」「Slack の自分名義で投稿する」といった外部アカウント名義の行動は、FS・MCP ツールに続く**第 3 の資源タイプ**として ACL に載せる。付与・承認・剥奪・監査がすべて既存の権限モデルで扱える。

- **クレデンシャルはプロキシが保持**し、エージェントには決して開示しない。プロキシが代理で実行する（モデル API キーと同じチョークポイントパターン）
- **代理（既定）**：bot / GitHub App 名義で実行し、人間への帰属は trailer で表現。スコープ付き・短命トークン
- **代替（opt-in）**：ユーザ委任トークンで本人名義として実行。外部からは本人と見分けがつかないため、明示的な権限付与と全件監査を必須とする
- **不可侵ルール：承認行為そのものは代理・代替の対象外**。エージェントが承認者のアカウントで承認できたら承認体系が無意味になる

## 外部ミラー

外部リポジトリ（GitHub 等）は**ミラー**であり、ワークスペース内の bare リポジトリが正。

- **sync-out（push）**：外部への公開行為として危険操作の承認ルーティングに乗る。実行はクレデンシャルプロキシ経由
- **sync-in**：外部側に直接積まれたコミットは取り込み時に author をプラットフォームユーザへマッピングして検証する。マッピングできないものは隔離して人間の判断に回す
